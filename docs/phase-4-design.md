# 阶段四设计：多任务跟踪、个人历史与结果恢复

状态：用户授权后，阶段四已完成实施与验证。本文记录需求依据、最终实现及验收证据；阶段五至七仍按任务清单推进。

更新日期：2026-11-02。

## 1. 结论与依据

阶段四完成制作流程的后半段。用户提交任务后可以继续制作，同时查看各任务的状态、当前阶段和结果。刷新页面后，页面从 Java 恢复个人记录并继续跟踪未完成任务。

现有 Java 接口与六表结构具备所需字段，本阶段没有新增接口或迁移。实施已按本文补充测试、代码与运行证据。

依据按以下顺序使用：

1. 用户当前指令及已确认的身份、工作线程数和编码规则。
2. [原始题目](../timu.md) 的正文要求，参考截图用于布局。
3. [需求、要求与任务清单](requirements-and-task-list.md) 的需求映射和实现基线。
4. 当前[接口文档](api.md)、[库表设计](database-design.md)及[阶段三设计](phase-3-design.md)。

[阶段一文档](phase-1-design.md) 保留为历史快照。可沿用其中未被后续结论取代的方案，但不恢复已更改的行为。例如，阶段三已选择提交后保留素材，本阶段继续保留。

## 4. 页面与交互

### 4.1 制作页 `/templates/[id]`

桌面布局参考原题 UI-02、UI-03：左侧集中模板信息、示例封面、素材要求、上传位和提交按钮；右侧展示“本模板记录”、刷新入口、任务卡片和“查看全部记录”链接。

左侧宽度以容纳上传操作为准，右侧使用剩余空间排列结果卡片。窄屏按制作区、记录区的顺序堆叠。小屏保留任务标题、状态、时间、错误和预览，不依赖鼠标悬停。

```text
产品导航 · 模板库 · 我的记录 · 当前演示身份
┌───────────────────┬──────────────────────────────────┐
│ 模板说明、封面     │ 本模板记录       刷新／查看全部记录 │
│ 素材要求、上传位   │ 任务 A     任务 B     任务 C        │
│ 开始制作          │ 状态／阶段／时间／结果或失败原因    │
│ 本次提交确认      │ 滚动追加                           │
└───────────────────┴──────────────────────────────────┘
```

任务受理后，页面将返回的完整 `Task` 合并到任务数据中，并立即显示该任务。提交按钮退出提交中，保留素材以便继续创建。修改素材只清除本次提交确认，不删除已创建的任务卡片。

任务受理结果未确认时，保留阶段三提示。用户可以刷新记录核对是否已受理；页面不能保证通过模板或时间自动识别同一次提交，也不会自动重发创建请求。

### 4.2 个人历史 `/history`

页面展示当前用户全部模板的任务，按创建时间和 ID 倒序排列。每条记录包含模板标题、创建时间、状态、当前或失败阶段，以及成功图片或失败原因。

历史支持滚动到底自动追加和手动刷新，不增加搜索、日期范围或批量操作。进入页面和刷新时恢复全部未完成任务，即使任务不在历史首屏也应继续跟踪。

未选择身份时显示身份选择提示，不发送个人查询。空历史显示可返回模板库的入口。身份切换后不沿用上一位用户的列表、cursor、错误和预览。

### 4.3 状态与结果

| 场景 | 界面表达 |
| --- | --- |
| `QUEUED` | 等待处理；不虚构阶段或队列名次 |
| `RUNNING` | 处理中；展示后台当前阶段名称 |
| `SUCCEEDED` | 制作成功；加载服务端 `resultUrl` 指向的私有图片 |
| `FAILED` | 制作失败；展示失败阶段和可理解原因；调度失败说明尚未开始执行 |
| 查询异常 | 状态暂时无法更新；保留上次成功读取的快照和时间，提供恢复查询 |
| 图片读取异常 | 保留任务成功状态；提示结果图片加载失败并允许重新加载 |
| 记录不可访问 | 提示记录不可访问；停止跟踪，不转成执行失败 |

当前阶段使用“素材检查”“模拟生成”“结果整理”。本阶段不绘制虚构百分比，也不通过定时器推进阶段。卡片显示当前阶段即可；逐步骤的开始、结束时间与展开面板不作为新增交付项。

结果预览请求应使用当前会话。切换身份时销毁旧预览；使用 Object URL 时应在替换或卸载后释放。预览读取到明确的 401 时触发既有会话失效流程。仅有图片加载错误时先显示图片错误，不推断任务执行失败。

## 5. 状态归属与数据合并

### 5.1 一个任务只有一个展示来源

`features/tasks` 维护完整 `Task` 类型、接口解析和按任务 ID 合并的规则。创建、历史、active 和 status 的响应均经过同一合并入口。制作页和个人历史使用同一套任务展示组件。

任务数据放入当前页面及身份作用域的 TanStack Query 缓存。历史分页只维护记录 ID、cursor 和查询状态。组件不另建一份可变任务状态，也不把请求失败写进 `Task.failure`。

上传和提交请求继续使用阶段三局部状态。展开、焦点、图片重试等展示状态留在对应组件。任务数据不写入 localStorage，刷新恢复依赖 Java。

页面作用域应包含用户 ID、身份版本和页面标识。历史索引再包含模板筛选。身份来源仍为 `IdentityProvider`，不建立第二套身份状态。

### 5.2 合并规则

1. 校验响应字段及当前请求的归属。
2. 按任务 ID 找到已知快照。
3. 新任务直接加入；已有任务只接受更大的 `version`。
4. 相同版本保持已知任务数据；较小版本直接丢弃。
5. 终态不接受返回等待或执行中的矛盾快照，界面保留终态并提示数据异常。
6. 根据合并后的任务计算待跟踪 ID，而不是根据刚返回的旧响应计算。

`version` 只在同一个任务内比较。它不是所有任务的全局序号，也不是进度百分比。历史响应覆盖范围之外的任务不能因为“本页没返回”而删除。

`missingIds` 表示记录不可访问。页面应移出对应跟踪 ID，隐藏旧内容和预览，显示不可访问提示。页面不能据此判断记录被删除或属于其他人。

### 5.3 提交与历史同时返回

历史首屏可能在新任务受理之前开始查询。旧首屏返回时，不能覆盖刚加入的任务。分页记录、已受理的新任务和已恢复的未完成任务按 ID 去重后展示。

创建响应仍保存受理时快照语义，但阶段三的状态提示将替换为简短的任务提交确认。卡片持续状态从统一任务数据读取，不在表单中再维护一个“实时任务”。

## 6. 查询生命周期

### 6.1 进入与刷新

确认身份后，并行读取历史第一页与 `/api/tasks/active`。两者独立显示加载和错误状态，单个接口失败不清空另一接口已返回的数据。

历史提供显示顺序，active 补充当前用户全部未完成任务。页面对已知未完成 ID 发起一次状态查询，再进入定时跟踪。不能只依赖历史第一页，也不能只轮询 active 来推断终态。

如果 active 初始化失败，提示未完成任务恢复不完整，并提供重试入口。已经从历史或本次提交发现的未完成任务仍可跟踪。active 重试成功后按 ID 合并，不能直接覆盖跟踪集合。

### 6.2 自动跟踪与停止

同一个页面只设一个批量查询协调者，卡片不各自启动轮询。待跟踪集合包含当前用户已知的全部未完成任务，与当前模板的显示筛选分开。

每轮最多 100 个 ID 一批，超过上限时依次分批。上一轮结束后约 2 秒发起下一轮，不使用可能重叠的固定间隔请求。新受理任务加入待跟踪集合，最迟在下一轮查询。

成功合并终态后，立即移出对应 ID。集合为空时不安排下一轮，也不为终态卡片另设自动查询。用户主动刷新历史不属于自动轮询。

任何一批发生网络异常、5xx 或响应解析错误时，保留已合并的数据并暂停该页面的自动轮询。显示查询异常和“恢复查询”。点击后对当前未完成 ID 重试，成功后恢复定时跟踪；失败则继续保留暂停状态。

终态尚未返回的任务即使从 active 消失，也不能直接判定成功。页面应通过 status 获取其最终快照。

### 6.3 页面、用户与浏览器状态

离开制作页或个人历史页时，停止定时器、取消页面请求并销毁任务作用域。进入另一个模板或历史页后从后端重新建立作用域。模板列表页不后台轮询任务，但 Java 已受理任务继续执行。

切换用户、退出、会话失效时，先使旧作用域失效，再取消查询和清除个人缓存。每个异步回调仍应校验作用域；取消请求只是减少工作，不能单独证明旧响应不会写入。

TanStack Query 不自行在窗口聚焦或网络恢复时重查任务。窗口焦点沿用阶段三的会话检查；发现身份变化或检查失败时，清理任务作用域。没有身份变化且轮询未暂停时，继续正常跟踪。

页面不可见时暂停新一轮自动查询；重新可见时，在身份检查完成后恢复未完成任务的查询。因错误暂停的查询不会因可见性变化自动重试。无待跟踪任务时不启动查询。

### 6.4 滚动分页与手动刷新

历史每页 20 条，使用后端返回的 `nextCursor` 原值，不自行解码或拼接。2026-11-03 按用户要求移除“加载更多”按钮：制作页滚动窗口、个人历史页面滚动到底时自动追加；当前内容不足以填满可见区域时继续补齐，直到没有下一页。追加期间仅显示加载状态，不并发重复读取。失败时保留已有记录并停止自动追加，通过“重新加载记录”重读首页后恢复；没有下一页时停止请求。

“刷新记录”重读历史第一页和 active，重新建立分页索引。刷新前保留已展示内容，只有成功结果才替换对应索引。刷新不删除本页面刚创建的任务，不让旧版本覆盖已有新状态。

首次加载、加载更多和刷新分别防止重复请求。刷新应使旧分页请求失效，旧 cursor 的迟到响应不能混入新列表。收到 `INVALID_CURSOR` 时保留已有记录并引导刷新，不反复请求同一无效 cursor。

## 7. 接口与库表影响

本阶段复用接口文档中的契约，不复制字段定义或改变枚举。

| 现有接口 | 本阶段用途 |
| --- | --- |
| `POST /api/tasks` | 受理后立即将完整 Task 加入页面记录 |
| `GET /api/tasks` | 当前模板或个人全部历史，cursor 分页 |
| `GET /api/tasks/active` | 初始化、刷新或主动重试时恢复全部未完成任务 |
| `GET /api/tasks/status` | 批量读取已知 ID，包含成功、失败终态及 missingIds |
| `GET /api/tasks/{id}/result` | 私有结果图片预览 |
| `GET /api/session` | 沿用身份确认、恢复与失效检测 |

`GET /api/tasks/{id}` 已能提供步骤详情，本阶段不要求额外增加详情界面。接口保留，不能为简化前端而改变后端步骤记录。

数据库没有计划变更。若实施发现缺口，应先记录具体需求、缺少的字段和验证场景，再更新接口或库表文档；不为了页面开发便利新增重复存储。

### 8.1 依赖方案

保留 Next.js 16.4.3、React 19.3.1、TypeScript 5.9.3、ESLint 9.39.5、Playwright 1.64.1，以及阶段二后端版本。本阶段已安装运行依赖 `@tanstack/react-query` 5.105.1，使用精确版本并更新锁文件。

2026-11-02 已在 Node 24.14.0 容器中安装该版本。React 和 `@types/react` peer 范围均为 `^18 || ^19`，覆盖项目主版本。全量浏览器回归、lint、类型检查及生产构建已通过。运行依赖 audit 为 0 项。

TanStack Query 用于请求缓存、取消和订阅。所有任务查询显式设置 `retry: false`、`refetchOnMount: false`、`refetchOnWindowFocus: false`、`refetchOnReconnect: false`。进入页面的首次读取由页面协调者发起。自动间隔只由批量协调者负责，避免库默认行为与业务生命周期重叠。离开页面清理当前任务查询和缓存；不增加浏览器持久化或开发工具依赖。

官方文档说明了查询默认重试、聚焦重查以及传递 `AbortSignal` 的取消方式。本稿据此要求显式配置，最终仍以项目行为测试为准：[默认行为](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)、[请求取消](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)。

```text
frontend/src/

      TaskScope.tsx                  页面与身份作用域、缓存订阅

      TaskResult.tsx                 结果读取、重试和资源释放
    creation/                        提交响应接入任务作用域
    identity/                        复用身份版本及会话失效能力
    templates/                       保留模板读取与说明展示
frontend/tests/                      多任务、查询故障、恢复与隔离验证
```

目录表达职责，不要求为每个函数另建文件。只建立实际使用的组件，不新增与 Next.js 路由约定冲突的 `src/pages` 层。页面组合放在 App Router 入口或对应私有组件目录。

完整任务类型归 `features/tasks` 所有。`creation` 可使用任务类型和受理回调，`tasks` 不反向导入上传表单，避免循环依赖。维持 `unknown` 边界校验、可辨识联合和 CSS Modules。

## 11. 设计走查与维护规则

| 走查发现 | 已纳入的设计 |
| --- | --- |
| 阶段三布局尚无历史区域 | 第 4 节重组左右分区，保留上传功能 |
| 精简回执缺少 version、时间和结果 | 第 5、8 节采用完整 Task 及唯一合并入口 |
| 只读取历史第一页会漏掉未完成任务 | 第 6 节同时恢复 active，并与显示筛选分离 |

| 阶段五才考虑布局会导致本阶段页面结构不符 | 第 4、10 节将主要布局和基本可用性纳入当前交付 |
| 不同页面保留多份任务状态容易漂移 | 第 5 节规定唯一任务数据与按 ID 归属 |

当前没有阻止实施的产品问题。`TaskController` 集中维护异步请求归属和单个轮询定时器，`TaskScope` 负责 React 生命周期与缓存订阅。代码采用普通类表达协调职责，没有再建立一套 Hook 状态或可变任务副本。

执行期间维护本文和任务清单。接口文档记录阶段四调用规则；没有协议变化时不重写字段契约。库表无变化时记录沿用结论。README 补齐页面入口、演示步骤、验证命令和限制，阶段三文档保留其交付时的快照边界。

实施先增加“连续受理两个任务后同时显示”的真实接口测试。测试因缺少任务区域失败后，再接入完整 Task 与任务区域。随后增加自动推进和刷新恢复测试，确认旧页面无法显示终态或恢复记录，再完成查询与历史接入。
