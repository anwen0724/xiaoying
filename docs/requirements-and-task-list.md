## 1. 目标与需求

实现一个可以独立运行的素材制作网站。用户浏览模板、上传图片并提交制作任务，在后台处理期间继续使用网站，最后查看个人历史记录和制作结果。

完整流程为：

**浏览模板 → 查看详情 → 上传图片 → 提交制作 → 后台处理 → 查看历史与结果。**

核心验收重点是 Java 后端的多步骤异步处理，以及前端的多任务状态管理。制作使用可控耗时、可指定失败阶段的模拟生成器，不需要真实 AI 或实际图片加工。

### 1.1 功能需求

| 功能 | 必须实现的行为 | 对应条款 |
| --- | --- | --- |
| 模板列表 | 展示分类、封面和标题；支持分类筛选和进入详情；数据从 Java 接口获取 | R-02 |
| 模板详情 | 展示标题、描述、示例封面和素材要求；按所需图片数量显示上传位 | R-03 |
| 素材上传 | 支持选择、预览、替换和移除；展示上传中和上传失败；校验数量、类型和大小 | R-03 |
| 提交任务 | 服务端校验并创建任务记录后返回任务 ID；Java 后台继续执行，关闭页面不影响任务 | R-04 |
| 多步骤处理 | 顺序执行“素材检查 → 模拟生成 → 结果整理”；保存整体状态、当前阶段、结果或失败原因 | R-05 |
| 模拟控制 | 能调整处理耗时，重复触发指定阶段失败；某一步失败后停止后续步骤 | R-06 |
| 前端任务跟踪 | 支持连续创建多个任务；分别展示阶段、状态、错误和结果；区分请求异常与任务执行失败 | R-07、R-08 |
| 历史与恢复 | 展示个人任务、创建时间和处理结果；刷新后从后端恢复记录，并继续跟踪未完成任务 | R-09 |
| 用户身份 | 自行设计身份识别和个人任务归属方式，在 README 中说明方案和演示方法 | R-10 |

### 1.2 关键行为约束

- 提交成功不等于制作完成。拿到任务 ID 后应展示任务，提交按钮不能一直停在“提交中”。
- 前端应区分素材上传中、提交请求中、任务等待／处理中、任务成功和任务失败。
- 查询失败不等于任务失败。查询接口暂时不可用时，应保留已有任务信息，并提供恢复查询的方法。
- 查询只能读取状态，不能通过查询请求推动后台执行，也不能只在前端定时切换阶段文案。
- 后台三个步骤必须有独立、可观察的执行边界；失败时保存失败阶段及可理解的原因。
- 整体状态至少能表达等待处理、处理中、成功和失败；整体状态与当前阶段可以分别设计。
- 完成后的任务不能因后续查询变回处理中。
- 各任务的状态、阶段、错误和结果互不串扰。
- 单个任务结束后停止对它的自动跟踪；没有未完成任务时停止轮询。
- 离开相关页面或切换用户时清理订阅和请求，避免旧响应覆盖当前用户或其他任务的数据。
- 刷新页面后恢复记录并继续跟踪未完成任务是必做项；服务重启后自动恢复执行不要求，但需说明限制。
- 素材未准备好或提交中时，避免重复点击提交。后端受理幂等不属于必做项。

## 2. 技术与工程要求

### 2.1 技术栈与数据职责

| 项目 | 要求 |
| --- | --- |
| 前端 | Next.js App Router、React、TypeScript |
| 后端 | Java、Spring Boot、MyBatis |
| 数据库 | MySQL |
| Java 职责 | 提供模板、素材、制作任务和个人记录相关业务接口 |
| 持久化 | 任务状态和历史记录保存到 MySQL |
| Next.js 职责 | 可直接调用 Java，也可提供接口中间层；不能独自承担业务执行和持久化 |
| 文件存储 | 后端本地目录或容器数据卷均可；不能只保留浏览器临时预览地址 |
| 版本 | 自行选择兼容版本，并在 README 中标明 |
| 可选技术 | 样式、客户端状态管理、异步执行和通知方案自行选择；不强制消息队列、Redis、SSE 或 WebSocket |

多任务可以排队或并行，不要求真正并行执行。模拟控制可以放在后端测试配置或开发接口中，不必暴露在正式页面或模板字段中。

### 2.2 模板与素材

- 自行构造模板，能够演示分类切换和不同图片数量要求。
- 模板可以保存在种子文件或数据库中，由 Java 接口读取；不要求模板 CRUD。
- 准备可访问的本地示例文件或合法可用资源，不依赖付费或公司内部服务。
- 前后端都要校验素材及制作参数，不能只依赖前端校验。
- 成功任务必须保存可预览的结果地址。
- 说明素材、脚手架和开源代码的来源及主要复用范围。

### 2.3 页面与基本可用性

参考截图的主要布局是：模板列表采用分类导航与图片卡片网格；制作页左侧展示模板信息和上传区，右侧展示任务历史与结果。

应参考主要布局，不要求品牌素材或逐像素复刻。未提供参考的区域可以自行设计。

- 桌面端完成主要界面，小屏下可以操作，不要求另做一套移动端设计。
- 页面具有清晰的信息层级、间距和状态反馈。
- 为加载中、空数据、模板不存在和请求失败提供可理解的提示。
- 按钮、输入和对话框使用合适的语义，保留键盘焦点。
- 为上传入口及图标按钮提供可理解的标签。

截图中的题外功能不扩展正文要求。账户设置、密码重置、账单、删除按钮等不因此成为必做项。

### 2.4 测试与 CI

提供在 `push` 或 `pull request` 时触发的 GitHub Actions，或者其他托管平台的等价流水线。压缩包交付也应包含 CI 配置。

| 范围 | 必需检查 |
| --- | --- |
| 前端 | lint、TypeScript 类型检查、构建 |
| Java | 测试和构建 |
| 后端关键测试 | 步骤执行顺序、失败后中断后续步骤 |
| 前端关键测试 | 多任务互不串扰、查询异常与任务失败的区分 |

不限定测试框架、测试数量和覆盖率，不要求端到端浏览器测试、自动发布或真实线上部署。

### 2.5 交付材料与 README

交付接受可读取的源码仓库、本地项目目录或源码压缩包，应包含：

- 完整前后端源码。
- 依赖版本和适用的锁文件。
- 数据库结构和初始化数据。
- CI 配置及 README。

仓库交付需注明验收 commit。源码压缩包不必包含构建缓存和依赖目录。最终通过收到任务的沟通渠道回复仓库链接或源码压缩包；提交日期按双方约定。

README 至少覆盖以下内容：

- 技术版本、项目结构、构建／测试／启动命令，以及前后端和数据库的连接方式。
- 配置项及不含真实凭据的示例、数据库初始化、模拟数据和素材准备方法。
- 主要接口及请求／响应字段、任务状态、阶段和后台执行方式。
- 成功、指定阶段失败、耗时调整、多任务和刷新恢复的演示方法。
- 用户身份与个人记录的设计及演示方法。
- 已完成／未完成项、已知限制、实际投入与取舍，包括未实现的服务重启恢复等边界。
- 基本部署与回滚步骤。
- 是否使用 AI；使用时说明任务拆解、上下文提供、代码生成／修改、验证和纠错流程。可以用一个具体例子，不必提供私人聊天记录、账号或全部提示词。
- 脚手架、开源代码和素材的来源及主要复用范围。

### 2.6 容器交付与验收环境

Docker Compose 是推荐项，不是硬性必做项。建议提供 Dockerfile、非敏感配置示例和初始化配置，使以下命令能够启动前端、Java 后端和 MySQL：

```sh
docker compose up --build
```

如果使用自定义配置文件名，需给出等价命令。即使不提供 Compose，也必须说明启动、配置及初始化方法。

评估者需要运行项目时，会在容器隔离环境中进行安装、构建、测试和应用执行，不在宿主机直接执行项目脚本。未提供 Compose 时，招聘方可能只审源码，或另行准备容器环境。

源码实现与实际运行效果分别记录。因环境或素材缺失而无法验证的部分应标记为未验证，不直接视为未实现。无需提供公网地址或真实部署截图。

## 3. 范围边界

### 3.1 不要求实现

- 真实 AI、真实图片加工、视频处理、支付服务。
- 复杂模板后台、积分会员体系、第三方账号接入、国际化。
- 多区域部署、集群和消息队列运维。
- 结果下载、删除、重新制作。
- 服务重启后自动恢复执行。

身份策略可以自行选择，不强制额外身份服务。后端受理幂等、断点续跑和自动重试可以在 README 中讨论取舍，不作为必做项。

### 3.2 当前实现基线

以下方案不是题目新增要求。身份和工作线程数已由用户确认，MyBatis-Plus 在后续讨论中保留。已交付版本见阶段二、三设计；阶段四的执行范围、新增依赖及验证见[阶段四设计](phase-4-design.md)。字段和接口分别以库表设计、接口文档为准。

| 决策 | 实现基线 | 需要验证的结果 |
| --- | --- | --- |
| 用户身份 | 两个可切换演示用户配合 Java 服务端会话，用户已确认 | 用户归属明确，刷新身份可恢复，切换用户后记录不混用 |
| 后端基础 | 复用用户初始化模板，保留 MyBatis-Plus 3.5.9，采用 Boot 3 Starter | 依赖解析、编译、启动和实际 MySQL 读写通过 |

| 素材与结果存储 | 本地目录配合容器数据卷 | 服务端可以访问，结果地址可用于前端预览 |
| 交付 | Docker Compose | 干净容器环境按文档启动并演示完整流程 |
| 技术版本 | 核心版本见阶段二设计；Maven 使用模板 Wrapper 3.9.14 | 本地容器与 CI 的构建、测试通过；辅助依赖在建立锁文件时核对 |

## 5. 执行前检查与最终验收

### 5.1 执行前检查结论

- 范围明确，无需为题外功能扩展开发。
- 身份方案必须先确定，因为任务受理、历史查询和前端用户切换都依赖它。
- 状态与阶段的接口约定必须先确定，否则前后端难以一致处理失败和刷新恢复。
- 可用素材是完整演示的前提，应在第一阶段准备。
- 模拟失败和耗时控制应随后台执行实现，避免到验收时才补演示能力。
- 阶段二执行时已重新确认 Docker 引擎可用，前后端及 MySQL 均已在容器中验证。

### 5.2 最终验收依据

以 R-01 至 R-13 的实现、测试及文档覆盖为必需验收范围，以 R-14 的容器交付作为推荐项单独记录。最终验收由题目评估者依据源码、自动化检查及可运行演示作出。

完成判据包括：核心流程可运行；后台三阶段顺序与失败中断有证据；前端多任务、请求异常和刷新恢复行为正确；用户记录归属明确；交付材料完整。

自动化测试、CI 结果、容器运行和场景演示共同支撑完成声明。仅有源码或仅有测试通过，不能替代尚未执行的运行验证。
