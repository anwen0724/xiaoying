# 后端模块与目录规范

## 本项目采用方式

2026-11-02 用户确认：目录结构不照搬本文示例，具体路径以 [阶段二设计](../phase-2-design.md) 为准。业务模块直接位于 `com.anwen.xiaoying` 下，采用 `identity`、`template`、`asset`、`task`，不额外增加 `modules` 层。

业务 Service 采用接口与实现类分离，分别放在所属模块的 `service` 和 `service/impl`。其余目录按实际职责创建，本文的目录示例不要求全部落地。

## 1. 模块边界与依赖

业务模块按业务职责划分，基础设施按通用技术能力划分。具体模块清单和迁移安排由项目设计文档定义。

- 业务模块位置由项目设计确定；`modules` 是可选的聚合目录，本项目不采用这一层。
- `infrastructure` 可存放不含业务规则的技术能力，有实际组件需要时再创建。
- 根 `config` 存放应用级装配；模块内部的 `config` 存放模块专属配置。
- `common` 存放少量共享基础类型，不收纳业务实体、业务 DTO 或业务规则。

业务入口通过 Service 执行业务。跨业务模块通过被调用模块提供的业务接口访问能力，不直接改写对方的数据表。跨模块只读查询不能绕过写入规则。

业务模块可以调用基础设施，基础设施和公共代码不反向依赖业务模块。应用配置负责组装具体实现。

## 2. 业务模块内部目录

以下是职责组织示例，目录按实际需要创建，不要求每个模块具备全部目录。本项目以具体设计中的模块路径替换 `<业务模块路径>`。

```text
<业务模块路径>/
├── api/
├── dto/
├── service/
│   └── impl/
├── entity/
├── mapper/
├── enums/
├── exception/
├── config/
├── parser/
├── validator/
└── converter/
```

| 目录 | 职责与规则 |
| --- | --- |
| `api` | HTTP Controller 和模块专属异常处理；取得身份、接收参数、调用业务接口、转换 HTTP 响应；不再嵌套 DTO 目录 |
| `dto` | 数据传输类型；HTTP 输入用 `Request`，HTTP 输出用 `Response`，事件用 `Event`，内部处理结果用 `Result`；不同用途分别定义类型 |
| `service` | 业务接口，表达模块提供的业务操作 |
| `service/impl` | 业务接口实现，负责业务规则、流程和事务 |
| `entity` | 持久化记录映射，不另设同义的 `model` 目录 |
| `mapper` | MyBatis Mapper 接口，负责数据库查询和写入 |
| `enums` | 有实际用途的枚举类型，不存放普通数据对象 |
| `exception` | 模块业务异常及对应错误定义 |
| `config` | 模块专属的 Spring 配置 |
| `parser` | 有独立解析职责的组件 |
| `validator` | 有独立职责的复杂内容校验组件 |
| `converter` | 需要复用或有独立规则的数据转换组件 |

业务 Service 采用接口与实现类。解析器、校验器等辅助组件不强制增加接口和 `Impl`。简单字段转换或局部检查放在所属方法中，不为每个动作创建一个类。

不设置含义笼统的 `support` 目录。不因流程有多个步骤，就增加步骤目录、协调器和多套 Service。存在独立业务职责时才拆分业务接口。

## 3. 数据类型

DTO 的结构由数据传递用途决定，Entity 的结构由持久化记录决定。Service 校验输入后，将有效数据写入持久化记录；查询时组织对应的响应 DTO。

外部输入和模型输出不直接作为持久化实体。数据库 ID、用户归属和业务状态由程序确定。内部处理结果与 HTTP 响应分别定义，避免内部格式变化直接影响接口契约。

## 4. 基础设施内部目录

基础设施按技术职责组织，不强制套用业务模块的 Controller、Service、Entity 结构。

| 目录 | 职责 |
| --- | --- |
| `client` | 外部能力客户端及其工厂、注册表 |
| `dto` | 通用技术请求、响应和用量类型，不引用业务 DTO |
| `config` | 技术组件专属配置 |
| `exception` | 技术能力的异常，不替代业务错误定义 |
| `producer` | 通用消息发送逻辑 |
| `consumer` | 通用消息接收和传输逻辑；业务事件消费者留在所属业务模块 |

具有明确技术职责的组件可以设置对应子目录。目录只在有对应文件时建立，不预建空目录。技术客户端是否需要接口，取决于现有契约和替换需要，不强制增加 Service 包装。

## 5. 资源与测试目录

- 提示词等业务资源按所属模块放在 `src/main/resources` 下，Java 类放在 `src/main/java`。
- Mapper XML 放在 `src/main/resources/mapper/<模块>`，namespace 对应 Mapper 接口全名。
- 测试放在 `src/test/java`，包结构对应被测代码。
- 包迁移时同步更新 import、扫描配置、Mapper namespace 和测试包；是否改变接口、表或消息协议由具体方案决定。

Java 命名、格式和事务要求见 [Java 开发规范](java-development-standard.md)。
